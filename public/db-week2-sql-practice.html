Practice for the PostgreSQL and SQL half of Week 2, using the lecture's own To Do List app. The todo_item table below has exactly the columns and types from the slides; I've added the lookup tables its *_id columns were meant to point at (the slides say “we will look at ways to link everything together”), so you can query real data. Every SQL answer here was run on a real PostgreSQL 16 server against exactly this data, with the output pasted underneath. Questions that change data either wrap the change in BEGIN … ROLLBACK (so nothing sticks) or tell you to re-run the setup script.

A. PostgreSQL, psql, users and security

Q1multiple choicepsql vs SQL

Which of these is a psql command rather than an SQL command?

Explanation

Answer: Lecture rule: psql commands start with a backslash; SQL commands end with a semicolon. psql is PostgreSQL's command-line client. Its backslash “meta-commands” are handled by psql itself and only work there; SQL commands are sent to the server and (mostly) work in any DBMS. Writing SQL keywords in upper case is a readability convention; most DBMSs aren't case-sensitive about keywords.

Q3roles6 marks

Write the lecture's command to create a user testuser with password 'password' that can log in and doesn't inherit privileges. Explain NOINHERIT, LOGIN and PASSWORD. What does \du then show for it, and what do SET ROLE and GRANT role_2 TO role_1 do?

Show answer
CREATE ROLE testuser
NOINHERIT LOGIN PASSWORD 'password';
  • Role: PostgreSQL's single concept for both users and groups. A role with LOGIN is effectively a user.
  • LOGIN: this role may connect. Without it, it's just a group of permissions.
  • PASSWORD 'password': sets its password. Single quotes, since it's a string literal.
  • NOINHERIT: if testuser is made a member of another role, it does not automatically get that role's privileges; it must explicitly run SET ROLE that_role; to act with them.
  • GRANT role_2 TO role_1; makes role_1 a member of role_2.
                             List of roles
 Role name |                         Attributes
-----------+------------------------------------------------------------
 postgres  | Superuser, Create role, Create DB, Replication, Bypass RLS
 testuser  | No inheritance

As the lecture notes, the new testuser shows no attributes except “No inheritance”: it isn't a superuser and can't create databases or roles. Compare postgres, the superuser.

Q4CREATE DATABASE5 marks

Write the lecture's statement creating database todo_list owned by testuser, UTF-8 encoded, with no connection limit, then connect to it as testuser. Explain ENCODING and CONNECTION LIMIT = -1, and why the owner matters.

Show answer
CREATE DATABASE todo_list
    WITH
    OWNER = testuser
    ENCODING = 'UTF8'
    CONNECTION LIMIT = -1;

\c todo_list testuser
  • OWNER: the owner can do almost anything with the database, which is why the lecture creates it for testuser rather than working as the superuser.
  • ENCODING = 'UTF8': UTF-8 is the character encoding that turns every character into bytes. It covers all languages and symbols, so “Zoë” or “€” store correctly.
  • CONNECTION LIMIT = -1: maximum simultaneous connections; −1 means no limit beyond the server's own.

I ran this on the practice server: \l todo_list then showed owner testuser and encoding UTF8. The first line is SQL (semicolon); the \c line is psql (backslash).

Q5permissionssecurity6 marks

(a) Why does the lecture warn against working as the superuser? (b) Write the commands to take away, then give back, testuser's permission to read public.todo_item. (c) What principle is this an example of? (d) On a newer PostgreSQL, creating a table as testuser gives “permission denied for schema public”. What fixes it?

Show answer

(a) A superuser has the highest level of access and can bypass all permission checks. Using it day to day is a security risk: one mistake, or one stolen password, can damage everything. So the lecture creates a separate user for a specific database.

REVOKE SELECT ON public.todo_item FROM testuser;
GRANT  SELECT ON public.todo_item TO   testuser;

(c) The principle of least privilege: give each user only the permissions they need (the slide's access-control picture of masked columns per user is the same idea).

(d) GRANT CREATE ON SCHEMA public TO testuser;. From PostgreSQL 15 onward, ordinary users no longer get CREATE on the public schema by default, so this grant is needed on 15+. (The slide's note says this “only works in 14 and below”. I believe it's the other way round, i.e. it's needed on 15+ and harmless on 14; worth checking on your install.)

Q6multiple choiceschemas

In public.todo_item, what is public?

Explanation

Answer: A PostgreSQL schema groups tables within one database: e.g. a management schema holding payroll tables and an employee schema with only daily-work tables, giving finer access control. public is the default schema, created automatically with every database. public.todo_item means “the todo_item table in schema public”; plain todo_item finds the same table. Note the two meanings of “schema”: Week 1's (the description/metadata of a database) and this one (a namespace).

Q7SQL injectionsecurity6 marks

A Java login page builds its query like this:

// username comes straight from a web form
String query = "SELECT * FROM app_user WHERE username = '" + username + "'";
ResultSet rs = statement.executeQuery(query);

(a) What query runs if someone types x' OR '1'='1 as the username, and what does it return? (b) Name three preventions from the lecture and rewrite the Java safely.

Show answer

(a) The input's quote closes the string early, and the rest becomes SQL:

SELECT * FROM app_user WHERE username = 'x' OR '1'='1'

'1'='1' is always true, so the WHERE is true for every row and the query returns every user. This is SQL injection: user input concatenated into a statement is interpreted as code, not data. Consequences on the slide: data leakage, tampering (insert/update/delete), even administrative control.

(b) Parameterised queries/prepared statements; input validation and sanitisation (allow-lists); principle of least privilege (so a compromised account can't do much).

// The ? is a placeholder. The driver sends the value separately,
// so it is always treated as data and can never change the query's structure.
PreparedStatement ps = connection.prepareStatement(
        "SELECT * FROM app_user WHERE username = ?");
ps.setString(1, username);          // fill placeholder 1 with the input
ResultSet rs = ps.executeQuery();
Graph link: this is the same root bug as many attacks in Security and Networks: mixing the control channel (code) with the data channel (input). Prepared statements separate them again.

Write CREATE TABLE for the lecture's room table (room_id like 'G0210', room_name, room_capacity, room_zoom) with room_id as primary key, insert the three rooms from the slide, and list rooms with Zoom that seat at least 50. The slide uses text for room_zoom with values 'yes', 'no', 'Yes'. What's the problem, and what type is better?

Show answer
Answer
CREATE TABLE public.room
(
    room_id       text NOT NULL,
    room_name     text,
    room_capacity integer,
    room_zoom     boolean,
    PRIMARY KEY (room_id)
);

INSERT INTO public.room VALUES
    ('G0210', 'Seminar Room', 50,  true),
    ('E1236', 'Lab',          40,  false),
    ('G0205', 'Auditorium',   100, true);

INSERT 0 3

--------------+---------------

(2 rows)

Column definition = name, data type, optional parameters (NOT NULL …). Column names follow Java-variable-like rules: no spaces, no special characters, can't start with a digit. room_id is text because 'G0210' contains letters; capacity is integer.

Q9constraints4 marks

The slides say we need both NOT NULL and PRIMARY KEY on todo_item_id. Predict the result of each, then run them:

INSERT INTO public.todo_item (todo_item_id, description) VALUES (1, 'Duplicate id');
INSERT INTO public.todo_item (description) VALUES ('No id at all');
Show answer
ERROR:  duplicate key value violates unique constraint "todo_item_pkey"
DETAIL:  Key (todo_item_id)=(1) already exists.
ERROR:  null value in column "todo_item_id" of relation "todo_item" violates not-null constraint
DETAIL:  Failing row contains (null, No id at all, null, null, null, null, null, null, null).

The first breaks uniqueness (id 1 exists), the second NOT NULL (no id given, so it's NULL). Together they're what a primary key means: never missing, never repeated (Week 1: PK = NOT NULL + UNIQUE). In PostgreSQL, PRIMARY KEY on its own already implies NOT NULL, so writing both is harmless but redundant. I'd still follow the slides' style in the test.

Q12INSERTforeign keys3 marks

The lecture's first INSERT example is below. It worked in the lecture, but fails on the practice database. Why?

INSERT INTO public.todo_item
VALUES (0, 'New Task', 0, 0, 0, 0, 0, '2022-02-02'::date, NULL);
Show answer
ERROR:  insert or update on table "todo_item" violates foreign key constraint "todo_item_owner_id_fkey"
DETAIL:  Key (owner_id)=(0) is not present in table "app_user".

In the lecture, todo_item had no foreign keys yet, so any integer was accepted. Here, owner_id REFERENCES app_user(user_id), and there's no user 0. Referential integrity stops a row pointing at something that doesn't exist. (Priority, context, status and project 0 would fail too; Postgres reports the first violation it finds.) This is the “links between tables” the FOREIGN KEY constraint protects.

Q13UPDATE4 marks

Mark item 3 as done today: set its completion date to 11 Oct 2026 and its status to 3. Show the row, then undo the change. How would the lecture's version set “today” automatically?

Show answer
Answer
BEGIN;

UPDATE public.todo_item
SET completion_date = '2026-10-11', status_id = 3
WHERE todo_item_id = 3;

SELECT todo_item_id, description, status_id, completion_date
FROM public.todo_item
WHERE todo_item_id = 3;

ROLLBACK;
Output (run on PostgreSQL 16)
UPDATE 1
 todo_item_id |     description      | status_id | completion_date 
--------------+----------------------+-----------+-----------------
            3 | Practice SQL queries |         3 | 2026-10-11
(1 row)

Structure: UPDATE table SET column = value, … WHERE condition;. The table, the columns, the new values, and which rows. The lecture writes SET completion_date = now(). now() is a built-in function returning the current date and time (stored in a date column, the time part is dropped; CURRENT_DATE gives just the date).

BEGIN starts a transaction; ROLLBACK undoes everything since; COMMIT would keep it. These are Week 1's ACID transactions, live. pgAdmin auto-commits each statement unless you use BEGIN.

Q14UPDATEtrap2 marks

Predict how many rows this changes, then run it (it's safely wrapped):

UPDATE public.todo_item
SET completion_date = now();
Show answer
Answer
BEGIN;

UPDATE public.todo_item
SET completion_date = now();

SELECT COUNT(*) AS rows_marked_complete
FROM public.todo_item
WHERE completion_date IS NOT NULL;

ROLLBACK;
Output (run on PostgreSQL 16)
UPDATE 12
 rows_marked_complete 
----------------------
                   12
(1 row)

All 12. No WHERE means every row. It's the most common destructive mistake in SQL, and the reason to try risky updates inside BEGIN … ROLLBACK first.

Q15DELETE4 marks

(a) Delete every item completed before 5 Oct 2026 (in a rolled-back transaction) and show which completed items remain. (b) Then try DELETE FROM public.priority WHERE priority_id = 1; What happens and why?

Show answer
Answer
BEGIN;

DELETE FROM public.todo_item
WHERE completion_date < '2026-10-05';

SELECT todo_item_id, description, completion_date
FROM public.todo_item
WHERE completion_date IS NOT NULL
ORDER BY todo_item_id;

ROLLBACK;
Output (run on PostgreSQL 16)
DELETE 3
 todo_item_id |       description       | completion_date 
--------------+-------------------------+-----------------
           12 | Submit DB practice test | 2026-10-10
(1 row)

Items 1 (4 Oct), 6 (30 Sep) and 8 (2 Oct) go. DELETE removes whole rows, so you never name columns. < on dates means “earlier than”. Rows with a NULL completion date aren't deleted: NULL < '2026-10-05' is unknown, not true.

(b)
ERROR:  update or delete on table "priority" violates foreign key constraint "todo_item_priority_id_fkey" on table "todo_item"
DETAIL:  Key (priority_id)=(1) is still referenced from table "todo_item".

Items still reference priority 1 (High), so deleting it would leave them pointing at nothing. The foreign key blocks it (default behaviour, NO ACTION), and nothing is deleted.

Q22NULLtrap3 marks

Find items that have no due date and aren't completed. Then explain why this returns nothing:

SELECT todo_item_id, description
FROM public.todo_item
WHERE due_date = NULL;
Show answer
Answer
SELECT todo_item_id, description
FROM public.todo_item
WHERE completion_date IS NULL
  AND due_date IS NULL;
Output (run on PostgreSQL 16)
 todo_item_id |  description   
--------------+----------------

(1 row)

--------------+-------------

NULL means “unknown”, and any comparison with unknown is itself unknown, so due_date = NULL is never true, even for NULL dates. WHERE keeps only rows where the condition is true. Q37indexesEXPLAINcheat sheet3 marks

Create an index on todo_item's owner_id and use EXPLAIN to see how WHERE owner_id = 2 is executed. Is the index used?

Output (run on PostgreSQL 16)

----------------------------------------------------------
 Seq Scan on todo_item  (cost=0.00..1.15 rows=1 width=64)
   Filter: (owner_id = 2)
(2 rows)

An index is a separate lookup structure (a B-tree, like a sorted map) that lets the DBMS find matching rows without reading the whole table, Week 1's CREATE INDEX constraint. EXPLAIN shows the plan without running the query; EXPLAIN ANALYZE runs it and reports real timings.

Surprise: it says Seq Scan (read every row). With 12 rows, reading the whole table is cheaper than consulting an index, so the planner ignores it. On thousands of rows it would switch to an Index Scan. Indexes are physical design (Week 1 step 5): they change speed, never results.
