A. Databases and DBMSs

Q1multiple choicedefinitions

Which is the Ramakrishnan & Gehrke definition of a database, as quoted in the lecture?

Explanation

Answer: the correct one is “a collection of data, typically describing the activities of one or more related organisations”. Of the others, “software designed to assist…” defines a DBMS (the software, e.g. PostgreSQL), “a set of tuples and attributes” is roughly a table/relation, and “a blueprint…” is a data model. The distinction the slides draw: the database is the data; the DBMS is the software that manages it. pgAdmin is neither: it's a client program that talks to the DBMS.

Q3why DBMS8 marks

A small climbing wall keeps member details in one Excel file, session bookings in another, and payments in a handwritten ledger. Using the four reasons from the lecture for needing a DBMS, describe one concrete problem for each and how a DBMS fixes it.

Show answer
  1. Data organisation and management. Without: scattered, partly unstructured files; finding one member's full history means searching three places by hand. With: a defined schema (tables with set columns) makes storage and retrieval systematic: one query answers it.
  2. Reduced redundancy and inconsistency. Without: a member's phone number sits in all three records; update one, forget another, and the data now contradicts itself. With: stored once, centrally, and linked by a member ID.
  3. Concurrent (multi-user) access. Without: two receptionists edit the bookings file at once and one save overwrites the other. With: concurrency control lets many users read and write simultaneously without conflicts.
  4. Data integrity and accuracy. Without: nothing stops a duplicate member ID or a negative payment. With: constraints, validation rules and data types enforce rules like “member ID must be unique”.
Graph link: concurrency here is the same problem as race conditions in Operating Systems. A DBMS transaction (later this page) is its answer, the database-sized version of a lock-protected critical section.
Q4multiple choiceDBMS tasks

The lecture lists seven major DBMS tasks. Which one is “protecting against unauthorised or malicious access”?

Explanation

Answer: Securing. The easy-to-mix pair: Protecting = against software or hardware malfunction (crashes, disk failure); Securing = against unauthorised or malicious access. The full seven: Defining (encoding the structure and constraints), Constructing (storing the data on a medium the DBMS controls), Manipulating (updating, querying, aggregating), Sharing (concurrent or sequential access by many users and apps), Protecting, Securing, Maintaining (evolving the database over its lifecycle).

Q5multiple choiceDBMS tasks

Writing CREATE TABLE … (room_id text NOT NULL, …, PRIMARY KEY (room_id)) is an example of which DBMS task?

Explanation

Answer: Defining: encoding the database structure and constraints. Inserting the rows afterwards would be Constructing (storing the data); SELECT/UPDATE would be Manipulating.

Q6multiple choicewhen not to use a DBMS

According to the lecture, in which case is a DBMS most likely not worth it?

Explanation

Answer: The slides give three cases where a DBMS may not pay off: very small/simple data (to-do lists, notes, where the overhead outweighs the benefit), highly unstructured or rapidly changing schemas (a relational schema is too rigid), and sometimes purely archival / bulk read-only data (optimised file formats or distributed file systems can be more efficient).

Q7multiple choicehistory

Who proposed the relational data model, and when?

Explanation

Answer: Edgar F. Codd (IBM), 1970. The slide's timeline: IBM's Information Management System (IMS), 1960, widely used; Bachman's first general-purpose DBMS at General Electric (the slide dates it 1970; most sources say early 1960s, I'd go with the slide in the test); Codd's relational model, 1970; through the 1980s the relational model spreads and SQL becomes the standard. Codd also introduced normalisation (Week 2).

B. Data models, the relational model and DBMS features

Q8data model3 marks

What is a data model, and what are its three purposes according to the lecture?

Show answer

A data model is a blueprint that defines how a database organises, stores and manipulates data, while hiding low-level details such as how bytes are laid out on disk. Its three purposes:

  • Abstraction: hides physical storage so you can focus on the logical structure.
  • Organisation & storage: defines how data elements relate (tables, keys, fields).
  • Operations: specifies the rules and commands to query, insert, update and delete.

The course focuses on the relational data model. The graph model (Week 5) is a different data model for the same job.

Q9multiple choiceschema

Which best describes a schema?

Explanation

Answer: The slide's key line: the schema is NOT the data, only a description of it, i.e. metadata. In the movies example, ACTOR(Name, Surname), DIRECTOR(Name, Surname), MOVIE(Title, Genre, Director, Leading actor) is the schema; “Steven Spielberg” or “Citizen Kane” would be data. (Week 2 adds a second meaning: a PostgreSQL schema such as public is a named container of tables inside one database.)

Q11redundancy6 marks

(a) Define redundancy. (b) Give the three causes from the lecture. (c) Why is it generally undesirable? (d) What is controlled redundancy, and when is it useful?

Show answer

(a) Storing the same information more than once.

(b) Repeating data (the same data in multiple places); storing derived attributes (they add no new data, a form of aggregation, but can be handy); adding checksums.

(c) Storage is inefficient (memory wasted) and management is error-prone: you must update several entries, so you're exposed to inconsistencies.

(d) Redundancy you add deliberately because it pays for itself: to protect against attacks/corruption (checksums), to save time when derived attributes are expensive to compute, and to improve query performance. Example: storing an order's total rather than summing its lines every time it's displayed.

Q13catalogviews5 marks

(a) What is the DBMS catalog, and what's odd about it?
(b) Define a view. Is a view's content normally stored?
(c) In the lecture's flights database, there's no table linking a baggage allowance to a booking. Explain how a view solves this.

Show answer

(a) A directory of information (metadata) about the data sets, files and databases managed by the DBMS: table names, column types, constraints, owners. The odd part: the catalog is itself a database, and managing it is complicated enough that some DBMSs have dedicated catalog managers. (psql's \dt and \d are queries against PostgreSQL's catalog.)

(b) An access to a subset of the information in the database; in practice a virtual table built from the base tables. Its content is often not stored permanently but computed on the fly; it can show data stored in base tables and/or data derived from them.

(c) From a booking's flight number you know the airline and the departure/destination countries, which is enough to look up the default allowance. A view such as FlightAllowance(FlightNumber, NumHandbags, SizeHandbags, NumCheckedBags, MaxWeight) works this out whenever it's queried, without storing a redundant allowance on every booking. (You'll write CREATE VIEW on the SQL page.)

Q14transactionsACID6 marks

(a) Define a unit of work and a transaction. (b) Explain why withdrawing cash at an ATM must be a transaction. (c) Name and define the four ACID properties.

Show answer

(a) A unit of work is any manipulation of the database (e.g. a collection of reads and writes) that is conceptually one thing. A transaction is a unit of work executed by a DBMS: its operations must all happen or none, otherwise the database can be left inconsistent.

(b) It's several steps: check credit, check daily limit, check the ATM has cash, subtract the amount, dispense. If only some happen (balance reduced but no cash dispensed) the data is wrong.

(c)

  • Atomic: treated as one unit; it either works completely or fails completely.
  • Consistent: leaves the database correct, so an illegal transaction can't corrupt it. (It doesn't promise a transaction is logically correct; incorrect ones simply fail.)
  • Isolated: even when run concurrently with others, the result is as if it had run alone.
  • Durable: once successful, its effects survive a system failure (power cut, crash).
Q15multiple choiceACID

Two transactions run at the same time. One reads a balance halfway through the other's transfer and sees money that has left one account but not yet arrived in the other. Which ACID property has been broken?

Explanation

Answer: Isolation: the result should be the same as if each transaction had run alone, so no one should see another's half-finished state. If instead the transfer itself had stopped halfway and stayed that way, that would be Atomicity. If a committed transfer vanished after a crash, Durability.

Q16constraints7 marks

Match each rule to the SQL constraint the lecture lists (NOT NULL, UNIQUE, PRIMARY KEY, FOREIGN KEY, CHECK, DEFAULT, CREATE INDEX):

  1. Age must be greater than 18.
  2. A car's plate cannot be empty.
  3. No two members may share an email.
  4. A booking's room must be a room that exists.
  5. New users get status “active” unless told otherwise.

Show answer

(a) CHECK   (b) NOT NULL   (c) UNIQUE   (d) FOREIGN KEY (it “prevents actions that would destroy links between tables”)   (e) DEFAULT   (f) PRIMARY KEY, which the slide describes as a combination of NOT NULL and UNIQUE   (g) CREATE INDEX (strictly a performance structure, not a rule about values).

A constraint is a restriction on which values may be inserted into a relation. Fingerprint image: it must be unique, so it is mathematically usable as a key, but images are slow to read and compare, so it's a poor practical choice. Use a short ID and keep the image as an ordinary attribute.

C. Informal design guidelines

Q17design guidelines8 marks

State the lecture's four informal design guidelines, then say which one each design breaks:

  1. MOVIE(Title, Genre, Surname1, Surname2)
  2. FILMOGRAPHY(ActorName, ActorSurname, Title) with “Orlando Bloom” on three rows
  3. CAR_OWNERS(PersonName, PersonSurname, CarBrand, CarModel, Plate) with most cells NULL
  4. Storing A(TheAttributeA) and B(TheAttributeB) only, and rebuilding C by combining them
Show answer
  1. Guideline 1: attributes with clear semantics → (a): which surname is the director, which the actor? Fix: DirectorSurname, LeadingActorSurname.
  2. Guideline 2: do not repeat information → (b): Bloom's name is stored per movie (update anomaly risk), and adding an actor with no movie forces a NULL Title, an insertion anomaly.
  3. Guideline 3: avoid attributes in a base relation whose values may frequently be NULL → (c): you can always merge tables into one big one, but NULLs waste memory, blur what attributes mean, and complicate aggregation (operations have to handle NULL). You can always split instead (the slide splits PHONE_DIRECTORY's sparse Landline/Mobile the same way).
  4. Guideline 4: avoid generating spurious tuples → (d): see the next question.
Q18spurious tuples5 marks

The lecture's relation C = {(a,1), (a,3), (b,1), (b,2)} is a subset of A × B with A = {a, b}, B = {1, 2, 3}.

  1. How many tuples does A × B have, and which are spurious?
  2. New one: A = {x, y, z}, B = {1, 2}, C = {(x,1), (y,2), (z,1), (z,2)}. Repeat (a).
  3. What are the two design choices on the slides, and which is better?
Show answer

A spurious tuple is a false row produced when tables are joined back together that wasn't in the original data. A × B (the Cartesian product) pairs every element of A with every element of B, so it has |A| × |B| rows.

(a) 2 × 3 = 6 tuples: (a,1), (a,2), (a,3), (b,1), (b,2), (b,3). C contains 4 of them, so the spurious ones are (a,2) and (b,3).

(b) 3 × 2 = 6: (x,1), (x,2), (y,1), (y,2), (z,1), (z,2). Spurious: (x,2) and (y,1).

(c) Scenario 1: store only A and B and build C on the fly by combining them, which saves memory but produces spurious tuples you must filter “manually”. Scenario 2: store C explicitly as well, which costs memory but has no spurious tuples. Scenario 2 is the better design. On the SQL page, CROSS JOIN is exactly this A × B.

Explanation

Answer: double ellipse (e.g. a researcher's Department). Q24junction tables4 marks

Using the lecture's reasoning, explain why you can't represent Student–Module (M:M) by putting a module_id column in STUDENT, nor by putting a student_id column in MODULE. What does the junction table do instead?

Show answer

A single column holds one value, not a list.

  • Attempt 1, module_id in STUDENT: fine if a student takes one module, but they take several. You'd need module_id_1, module_id_2, …, and how many? That's the repeating-group problem Week 2's 1NF forbids.
  • Attempt 2, student_id in MODULE: the same problem in reverse; a module has many students.

The junction table ENROLMENT(student_id FK, module_id FK, enrolled_on) has one row per (student, module) pair. In the lecture's words, it turns one hard problem (many-to-many) into two easy ones (one-to-many, twice): one student → many enrolment rows; one module → many enrolment rows. It's also where attributes of the relationship itself go (enrolled_on, a grade).

E. JDL (JHipster Domain Language)

Q26multiple choiceJDL

What is JDL?

Explanation

Answer: JDL = JHipster Domain Language. You describe entities (like a Java/UML class with attributes but no operations) and relationships as text; JHipster (a web application stack generator, run with the jhipster CLI) generates the database tables, backend, APIs and basic frontend from it. Reasons the slides give for JDL: text-based, easy to modify, version-control friendly, less ambiguous than hand-drawn diagrams, generates code, integrates with JHipster. It bridges the gap between an ER diagram (data only) and a real app (behaviour, APIs, services, frontend). Try it at JDL Studio.

Q27JDL types6 marks

Choose the JDL type for each field: (a) a product price in pounds and pence; (b) a date of birth; (c) a member's long bio; (d) a profile photo; (e) whether a member is active; (f) a moment a payment happened; (g) a stock count; (h) a globally unique ID.

Show answer

(a) BigDecimal, exact decimals; never Float/Double for money, which can't store 0.10 exactly (the same reason you'd use BigDecimal for money in Java). (b) LocalDate, a date without time zone. (c) TextBlob, a large block of text. (d) ImageBlob. (e) Boolean. (f) Instant, a moment in time (or ZonedDateTime if the time zone matters). (g) Integer (Long for huge counts). (h) UUID.

Types are capitalised class-like names. The real parser rejects int or string: type names must start with a capital letter.

Q29multiple choiceJDL

Q32JDL debugging6 marks

Find four problems in this JDL (three stop it parsing; one parses but means the wrong thing):

entity Lecturer {
  name string required,
  officeHours List<String>
}
entity Module {
  code String required unique,
  credits int
}
// intended: one lecturer teaches many modules
relationship OneToMany {
  Module{lecturer} to Lecturer{modules}
}
Show answer
  1. string → String. Type names must start with a capital (real parser error: “typeName must match /^[A-Z][A-Za-z0-9]*$/, got string”).
  2. List<String>: JDL has no List/Set types (syntax error on <). Make OfficeHour an entity with a relationship.
  3. int → Integer, same capitalisation rule.
  4. The relationship is reversed. OneToMany { Module … to Lecturer … } says one module has many lecturers. It should be Lecturer{modules} to Module{lecturer}: the “one” side first.

Fixed version:

entity Lecturer {
  name String required
}
entity Module {
  code String required unique,
  credits Integer
}
relationship OneToMany {
  Lecturer{modules} to Module{lecturer}
}

(Errors 1–3 confirmed by running the JDL parser; the fixed version parses.)
